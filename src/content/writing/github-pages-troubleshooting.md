## 先把问题分成三层

个人网站“打不开”可能发生在三个完全不同的阶段：仓库没有产生可部署文件、Actions 没有成功发布、浏览器请求了错误地址。只盯着最后一层的 404，很容易反复修改无关配置。

推荐的排查顺序是：

1. 本地构建是否成功，输出目录里是否存在入口文件；
2. Actions 的构建与部署是否分别成功；
3. Pages 的发布源是否指向这条工作流；
4. 最后再检查域名、仓库名和资源路径。

## 用户主站与项目站不是同一种路径

用户名主站通常使用 `用户名.github.io` 仓库，并发布在根路径；项目站则通常位于 `用户名.github.io/仓库名/`。这个差异会影响站点 canonical 地址、静态资源和内部链接。

对于主站，站点地址应保持为根地址，不要把仓库名再拼进路径。以本站为例：

```text
https://nineanswerer.github.io/
```

用户主站的完整仓库名应为 `<用户名>.github.io`，其中用户名部分必须准确。旧站曾经把 `nineanswerer` 少写了字符，造成路径和预期不一致。修改仓库名后，本地远端也要同步：

```bash
git remote set-url origin https://github.com/nineanswerer/nineanswerer.github.io.git
git remote -v
```

项目站则需要显式配置 base path。不能因为在本地根路径预览正常，就假设线上子路径也能正常工作。

## 编码问题要用文件证据定位

旧笔记曾把 PowerShell 与 UTF-16 简单画等号，这并不准确：编码行为与 PowerShell 版本、命令和重定向方式有关。可靠的做法是直接检查生成文件，终端类型只能作为线索。

配置文件和 Markdown 应统一保存为 UTF-8。遇到解析器在文件开头报出奇怪字符时，可以检查是否存在 BOM、不可见字符或错误编码，并用编辑器明确转换后重新构建。

```bash
file hugo.toml
git diff --check
```

`file` 可用于辅助识别编码与换行，`git diff --check` 则适合发现空白错误。它们用于缩小问题范围，实际构建仍需单独运行。

## “最新版”不一定是最稳妥的 CI 版本

本地和 CI 使用不同的 Hugo、Node 或主题版本时，同一仓库可能出现不同结果。旧站曾遇到 Actions 默认 Hugo 版本无法解析新主题配置的情况。

解决思路是明确构建工具版本，并保留锁文件。对 Hugo 主题，需要确认主题要求的最低版本以及是否需要 Extended；对 Node 项目，则应固定 major 版本并提交依赖锁文件。

“安装最新版”偶尔能绕过旧问题，却也会引入新的不兼容。更可复现的选择是：**明确版本、记录兼容范围、让本地和 CI 使用同一套依赖。**

## Actions 成功不等于页面已经更新

部署工作流通常包含构建、上传制品和发布等步骤。绿色对勾说明这次运行完成，但浏览器仍可能受缓存影响，或者你检查的地址并不属于这次发布。

可以按下面顺序确认：

- 工作流是否由目标分支的提交触发；
- 上传的制品是不是本次构建的输出目录；
- Pages 是否选择 GitHub Actions 作为来源；
- 打开页面后检查关键内容或资源哈希是否更新。

强制刷新只适合排除浏览器缓存，发布源和构建路径需要分别修正。

## 保留一张最小检查清单

每次部署后，至少检查首页、一个详情页、一个静态资源和移动端页面。若网站包含 RSS 或 sitemap，也应确认它们指向公开域名而不是本地地址。

排错需要建立一条可重复的因果链：**源码产生构建产物，工作流发布产物，浏览器访问发布地址。** 哪一环断开，就在哪一环取证。
