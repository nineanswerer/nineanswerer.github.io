## 最开始，只是想有一个自己的平台

这个网站没有宏大的立项理由。最开始看到别人有自己的网站，我也想试试；后来觉得在里面发内容挺好，现在又希望它能用于简历，让别人更具体地看到我的项目和能力。

这几个目的并不冲突，但“给别人看”很容易悄悄变成“做给别人看的宣传页”。两次改版最有价值的地方，就是我逐渐看清了这之间的区别。

## 第一次改版：项目终于有了上下文

旧站使用 Hugo 和 PaperMod，能发布文章，也有搜索与目录，但测试文章和泛化介绍占据主要位置，项目只剩链接。别人即使来到网站，也很难知道我究竟做过什么。

第一次重构选择 Astro，把项目与文章拆成不同的 Content Collection。项目页开始包含职责、状态、技术栈、源码、发布入口和验证边界，项目展示因此有了完整上下文。

这次改版解决了项目证据不足的问题，也建立了后续写作需要的内容结构。但它很快走向了另一个极端。

## 为什么“工程档案”还是不像我的网站

当时的布局、颜色搭配和视觉焦点，都让我想到广告、宣传页面或公司大屏。大标题、代表案例和指标带很醒目，却不像一个真实的人正在写作和制作东西的地方。

我否定它，因为所有内容都被统一成确定、完整、值得宣传的样子。可我的项目有不足，文章还在积累，有些设计也会被自己推翻。网站如果只展示结论，就把这些最有个人特点的部分抹掉了。

第二次改版重新安排谁是主角：项目是证据，作者、写作和近期活动也应该在首页。

## 第二次改版：把工作台真的用起来

现在的首页先介绍九术，再出现近期更新、正在制作的项目、长文与碎片。内容被分成三种阅读尺度：

1. **长文**保留完整过程、技术取舍和验证边界；
2. **碎片**记录一个具体决定或容易重犯的错误；
3. **项目页**集中交代问题、职责、方案、证据和不足。

视觉上，方格纸、九宫格和墨迹批注代替统一的宣传卡片。小目录树使用 SVG，首页保持轻量。没有真实头像时，以“九”字印章作为识别。

这版比上一版更接近我想要的个人网站，但它仍然不够好。当前样式会随着真实内容继续调整。

## 框架与组件服务于内容

网站没有账号、数据库或服务端业务，主要内容是 Markdown 和少量交互，因此继续使用 Astro 静态输出，配合 GitHub Actions 和 GitHub Pages。

项目、长文、碎片与现在页拥有各自的内容模型。统一内容函数把写作合并成时间流、本地搜索索引与 RSS，避免每个页面各写一套数据逻辑。

主题切换、站内搜索、博客筛选和代码复制都是渐进增强。即使脚本没有执行，导航、项目和文章仍然可读；旧 Hugo 链接使用静态跳转页，不依赖客户端路由。

标题和短批注使用本地托管的 LXGW WenKai 子集，正文使用系统中文字体。字体只保留本站实际出现的字符，许可随文件保留。

## AI 协作与内容确认

我提出建站目的、否定过于公司化的视觉方向、决定保留个人工作台的路线，并确认最终内容；AI 协助框架搭建、组件与样式实现、测试和文章草稿。

这次写作之前，我特意补了一轮访谈。技术栈可以从仓库确认，建站目的、否定上一版的原因和个人决策由我本人确认。

## 和数据科学专业有什么关系

这个静态博客与数据科学专业的联系，主要在于内容结构和证据表达。

相关部分是把分散内容整理为有类型的数据，派生时间流、搜索和订阅，再用可读结构表达项目证据。同时，写作需要区分事实、解释和无法证明的部分。

未来它可以承载更多真实的数据处理与可视化文章，成为我展示专业能力与技术表达的长期入口。应该先有值得展示的问题和结果，再决定是否需要图表或交互。

## 验证从“能打开”走到“继续可用”

网站在构建前运行 Astro 类型检查，再使用本机 Edge 和 `playwright-core` 检查不同宽度、横向溢出、图片比例、键盘交互、主题、搜索、订阅和旧链接。

这次还实际遇到了截图纵向拉伸：原始图片尺寸和 HTML 属性都正确，但 CSS 强制宽度后没有覆盖固定高度。修复之外，测试开始比较图片的自然宽高比与渲染宽高比，避免下一篇内容再次踩中同一个问题。

测试脚本自己启动临时服务器，并在结束时关闭；截图用于检查真实排版，同时核对 HTTP 响应。依赖版本、静态跳转、无 JavaScript 阅读和自动部署也都留在仓库里，方便别人复核。
