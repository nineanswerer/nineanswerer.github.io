## 最开始，只是想有一个自己的平台

这个网站没有宏大的立项理由。最开始看到别人有自己的网站，我也想试试；后来觉得在里面发内容挺好，现在又希望它能用于简历，让别人更具体地看到我的项目和能力。

这几个目的并不冲突，但“给别人看”很容易悄悄变成“做给别人看的宣传页”。两次改版最有价值的地方，就是我逐渐看清了这之间的区别。

## 第一次改版：项目终于有了上下文

旧站使用 Hugo 和 PaperMod，能发布文章，也有搜索与目录，但测试文章和泛化介绍占据主要位置，项目只剩链接。别人即使来到网站，也很难知道我究竟做过什么。

第一次重构选择 Astro，把项目与文章拆成不同的 Content Collection。项目页开始包含职责、状态、技术栈、源码、发布入口和验证边界，为截图与技术栈补充了项目上下文。

这次改版解决了项目证据不足的问题，也建立了后续写作需要的内容结构。但它很快走向了另一个极端。

## 为什么“工程档案”还是不像我的网站

当时的布局、颜色搭配和视觉焦点，都让我想到广告、宣传页面或公司大屏。大标题、代表案例和指标带很醒目，却不像一个真实的人正在写作和制作东西的地方。

我否定的是那种统一、完整、充满宣传感的表达。我的项目有不足，文章还在积累，有些设计也会被自己推翻。这些过程更能体现网站的个人特点。

所以第二次改版重新安排了首页的主角：项目作为证据，作者、写作和近期活动也占据明确位置。

## 第二次改版：把工作台真的用起来

现在的首页先介绍九术，再出现近期更新、正在制作的项目、长文与碎片。内容被分成三种阅读尺度：

1. **长文**保留完整过程、技术取舍和验证边界；
2. **碎片**记录一个具体决定或容易重犯的错误；
3. **项目页**集中交代问题、职责、方案、证据和不足。

视觉上，方格纸、九宫格和墨迹批注代替统一的宣传卡片。小目录树只用 SVG，三维结构留在应用中。当前使用“九”字印章作为头像标识。

这版比上一版更接近我想要的个人网站。当前样式会继续随着真实内容调整，每次改动都有实际内容作为依据。

## 框架与组件服务于内容

网站没有账号、数据库或服务端业务，主要内容是 Markdown 和少量交互，因此继续使用 Astro 静态输出，配合 GitHub Actions 和 GitHub Pages。

项目、长文、碎片与现在页拥有各自的内容模型。统一内容函数把写作合并成时间流、本地搜索索引与 RSS，避免每个页面各写一套数据逻辑。

主题切换、站内搜索、博客筛选和代码复制都是渐进增强。即使脚本没有执行，导航、项目和文章仍然可读；旧 Hugo 链接使用静态跳转页，不依赖客户端路由。

标题和短批注使用本地托管的 LXGW WenKai 子集，正文使用系统中文字体。字体只保留本站实际出现的字符，并随文件保留许可。图片使用真实项目截图和个人内容素材。

## AI 协作与经历确认

这次开发采用 AI 协作。我提出建站目的、否定过于公司化的视觉方向、决定保留个人工作台的路线，并确认最终内容；AI 协助框架搭建、组件与样式实现、测试和文章草稿。

写作前，我补了一轮访谈。技术栈可以从仓库确认，建站目的、设计取舍和个人分工则通过访谈记录。

简历中的职责写为“个人内容模型与产品表达、AI 协作完成静态网站、自动化界面验收”。

## 和数据科学专业有什么关系

这个静态博客与数据科学专业的联系，是把分散内容整理为有类型的数据，派生时间流、搜索和订阅，再用可读结构表达项目证据。写作中也尽量区分事实、解释和证据边界。

未来它可以承载更多真实的数据处理与可视化文章，成为我展示专业能力与技术表达的长期入口。先有值得展示的问题和结果，再决定图表或交互的形式。

## 验证从“能打开”走到“继续可用”

网站在构建前运行 Astro 类型检查，再使用本机 Edge 和 `playwright-core` 检查不同宽度、横向溢出、图片比例、键盘交互、主题、搜索、订阅和旧链接。

这次还实际遇到了截图纵向拉伸：原始图片尺寸和 HTML 属性都正确，但 CSS 强制宽度后没有覆盖固定高度。修复之外，测试开始比较图片的自然宽高比与渲染宽高比，检查下一篇内容是否出现同类问题。

测试脚本自己启动临时服务器，并在结束时关闭；截图用于检查真实排版。依赖版本、静态跳转、无 JavaScript 阅读和自动部署也都留在仓库里，方便别人复核。
