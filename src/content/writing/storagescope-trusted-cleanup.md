这轮整改没有从“再加一种清理能力”开始，而是先撤回了一个过强的承诺：**目录名叫 `cache`，不等于整棵目录都能安全删除；文件进入回收站，也不等于磁盘空间已经释放。**

StorageScope 已经有扫描、快照、3D 目录树和清理入口。功能流程看起来闭合了，但“能执行”并不代表“值得信任”。这次主要做的，是把建议、计划、执行和结果重新分开，让每一步都有证据，也让失败能够停在文件变化之前。

## 事实卡：这轮验证到底覆盖了什么

| 项目 | 本次实际范围 |
| --- | --- |
| 实现层 | Rust 清理计划与执行复核、Tauri 命令桥接、React 保留边界与结果界面 |
| 自动化 | Rust 核心 29 项、桌面桥接 2 项、前端模型 14 项测试；前端构建与 lint |
| 回收站实景样本 | 工作区内 8 个初始文件、16.0 MiB，另加日志文件和分析后新增的 36 B 文件 |
| 合并实景样本 | 3 个路径，各有一份 2.0 MiB 的相同内容 |
| 真实窗口结果 | 变化目录完整跳过；2 个选中文件进入回收站；3 个合并路径保留并共享同一文件实体，核实释放 4.0 MiB 分配空间 |
| 尚未覆盖 | 第三方设备复现、所有特殊文件系统、回收站清空后的卷余量测量、普遍性能结论 |

真实窗口验收使用的是当前桌面调试版本。正式 NSIS 安装包另外完成了构建；这两件事不混写为“安装包已在多台设备验证”。

## 第一个问题：名称只能提供线索，不能提供删除证明

旧规则容易把“缓存”“日志”“临时目录”等名称解释成安全等级。问题在于，名称无法回答三个关键事实：目录属于哪个应用、内容是否还能重建、其中有没有用户主动放入的资料。

因此，现有目录名规则不再直接给出“可安全清理”的结论，而是统一作为人工复核线索。`Recommended` 等级仍保留给未来证据更完整的规则，例如能够确认应用身份、路径边界和重建范围的场景，但当前这些通用名称规则不会仅凭名字达到这一级。

界面也撤下了“一键安全释放”。用户仍然可以处理候选，但必须先看到判断依据并明确选择，而不是让一个绿色数字替自己做决定。

## 第二个问题：分析完成时正确，执行时可能已经过期

清理分析和实际执行之间，文件可能新增、修改或被替换。只保存一个待删路径，不能保证稍后处理的还是当初看到的对象。

这次给执行计划加入了扫描基线：

- 目录记录逻辑大小、文件数和确定性的后代清单指纹；
- 文件记录大小、修改时间和可获取的文件实体身份；
- 执行前重新解析路径，并拦截越出扫描根的链接、扫描根本身和 Windows 系统关键目录；
- 目录在执行前重新扫描，指纹或数量发生变化就跳过，而不是继续删除整棵目录。

真实窗口验收中，我在分析结束后向 `cache` 新增了 `late-arrival.tmp`。执行结果是这个目录完整跳过：原有文件和新增文件都还在。与此同时，另外两个没有变化的选中文件正常进入回收站。

这个案例比“删除成功”更重要，因为它验证了系统能够在条件变化时选择不做。

## 保留边界不是一句提示，而是两层约束

重复文件还有一个独立问题：内容相同不代表路径多余。某些目录可能是原件、项目输入或用户明确不想触碰的区域。

现在可以设置两类相对路径：

- **参考目录**：重复组的保留锚点，组内存在参考副本时优先保留；
- **排除目录**：不参与本次清理。

两者都保护目录自身和后代，也保护其祖先目标，避免通过选择上级目录绕过边界。前端会禁用对应勾选并调整已选集合，Rust 执行层还会再次检查，不把安全寄托在界面状态上。每组重复文件至少保留一份，也在计划生成时再次约束。

## 三种空间数字，回答三个不同问题

这次把界面和执行报告中的空间口径拆开了：

| 数字 | 它实际说明什么 |
| --- | --- |
| 候选逻辑大小 | 文件长度意义上的分类估算；缓存与重复组可能重叠，不等于可释放空间 |
| 待清空回收站大小 | 已成功移入回收站的逻辑大小；仍可恢复，不能记作已实际释放 |
| 已核实分配空间释放 | 硬链接合并后，按已移除独立实体的分配大小统计的结果 |

Windows 下，合并结果使用 `FILE_STANDARD_INFO.AllocationSize` 获取分配大小。只要任一已合并项无法完整核实，总量就显示“无法完整核实”，不会拿文件逻辑大小补齐一个看似精确的数字。

在合并样本中，3 个 2.0 MiB 路径合并后仍然全部存在，内容一致，`fsutil hardlink list` 也确认它们属于同一组硬链接。移除两个独立副本后，报告为合并逻辑大小 4.0 MiB、已核实分配空间释放 4.0 MiB。前者描述处理对象，后者才是这次能够核实的空间结果。

清理后还可以保存结果快照，与分析时自动保存的基准快照比较。但快照记录的是文件清单和逻辑大小变化，**不是卷可用空间测量器**。回收站是否清空、其他程序是否同时写入，都不能靠这张差异表替代判断。

## 实景验收还抓到了一个界面问题：执行后候选会“复活”

第一轮合并验收的文件结果是正确的，但截图暴露了一个状态问题：重复组撤下后，原本被它隐藏的大文件条目重新出现，候选逻辑大小也停留在执行前。

换句话说，底层做对了，界面却像又发现了一批新候选。

后来把执行后的状态更新收敛为同一个重算过程：已移入回收站的目标及其基线被撤下；已合并副本从重复组、大文件和执行基线中一起移除；候选逻辑大小根据剩余项目重新计算。新增模型测试覆盖这两种情况，真实窗口复验也确认合并后只剩 1 个大文件条目、0 个重复组，不再出现副本“复活”。

## 分工与下一步

我主导产品定义、交互决策和真实场景验收，AI 协作实现、调试与文章整理。这里记录的是这轮实际修改和本机观察，不把协作过程包装成全部代码独立手写，也不把测试样本扩大为普遍安全保证。

下一步更有价值的不是继续增加“可删”类别，而是补公开复现脚本、CI 和更多真实应用规则。只有能说明规则证据、复核失败原因和空间结果来源，清理功能才算真正可用。
